# 04 — Decision log

Append-only. Numbered, dated, with status. Any architectural change gets an entry here.
Status: `accepted` · `accepted (revisit)` · `open` · `superseded by NNN`

---

### 001 — The LLM does not run the agent loop
**Date:** 2026-08-29 · **Status:** accepted

Exactly two narrow LLM calls per turn: schema-constrained state extraction, then response
generation from a restricted fact packet. Reconciliation, conflict detection, next-action
choice, search, ranking and pricing are deterministic Python.

*Why:* the rubric is 30% reliability and 25% AI system design. An autonomous tool loop
makes tool selection non-reproducible, permits hallucinated numbers, and hides the
decision-making being graded. It also makes the eval harness affordable, since the
deterministic middle is testable without a model.

*Cost:* less flexible than a free-running agent; every new behaviour needs a policy branch.
Accepted — legibility is the point.

---

### 002 — No agent framework, no vector DB, no RAG
**Date:** 2026-08-29 · **Status:** accepted

Custom loop, roughly 400 lines. The data is structured, so retrieval is a query.

*Why:* a framework hides exactly the reasoning being evaluated, and embeddings over a
structured catalogue would read as pattern-matching rather than judgment. RAG's real
place here is unstructured policy documents and reviews — noted in the engineering note,
not built.

### 003 — Dev LLM backend is the local Claude Code CLI on Haiku
**Date:** 2026-08-29 · **Status:** **open — must be resolved in Phase 6**

Development runs against `claude -p --model haiku --output-format json` behind the
`LLMClient` interface. Free, and Haiku handles schema-constrained extraction well.

*Open risk:* a reviewer at Mehman cannot run a local Claude Code subscription, and the
brief requires the system to actually run. Resolution options, to be picked in Phase 6:
an `AnthropicClient` with an API key, or a `ReplayClient` demo mode that runs with no
credentials at all. Do not let this reach the deadline unresolved.

### 004 — Pricing is deterministic application logic
**Date:** 2026-08-29 · **Status:** accepted

The LLM never produces a number. `calculate_quote` returns a line-item breakdown; the
response model may quote it and never recompute it. Unit-tested against hand-computed
fixtures.

*Why:* the brief asks for this explicitly, and prices are the single most damaging thing
to get wrong.

---

### 005 — Grounding is a mechanism, not a prompt instruction
**Date:** 2026-08-29 · **Status:** accepted

The response model sees only a `GroundingPacket`. A validator then checks every number,
property name and room name in the draft against that packet. Failure triggers one repair
pass, then a deterministic template. The verdict is recorded and shown in the UI.

Dataset fields distinguish `known` / `not_applicable` / `unknown`; nothing is implicitly
false. This is what makes "is the pool heated?" answer honestly.

### 006 — 24 properties, not the 3 the brief asks for
**Date:** 2026-08-29 · **Status:** accepted

Eight cities, 2–5 room types each, roughly 70 room types. Sixteen generated by a seeded
script, eight hand-authored to plant specific edge cases.

*Why:* three properties cannot exercise search, ranking or near-miss behaviour honestly.
*Risk:* dataset work becoming a time sink — bounded by generating most of it and
hand-authoring only the fixtures the edge cases need.

### 007 — JSON is the source of truth; SQLite is a build artifact
**Date:** 2026-08-29 · **Status:** accepted

Catalogue JSON lives in git and stays human-readable and reviewable. It is loaded into
SQLite at boot for indexed querying. The `.db` is never committed.

*Why:* a reviewer can read the data; the query layer still gets real indices and a
credible path to Postgres.

---

### 008 — Pruning is non-lossy: exact plus near-miss buckets
**Date:** 2026-08-29 · **Status:** accepted

Search returns `exact[]` and `near_miss[]`, the latter carrying a typed `Relaxation`
(`date_shift`, `over_budget`, `capacity_split`, `policy_conflict`, `min_stay`). Candidates
are dropped only past a threshold: more than ±2 days out, more than 20% over budget, or
needing more than 2 rooms.

*Why:* naive pruning discards the most persuasive results. A property free two days later
is a better conversation, not a miss. This is also how "no availability, suggest the best
alternative" should actually feel.

*Honest note:* at 24 properties this is not needed for speed. The value is the interface,
which survives the move to Postgres `daterange` + GiST.

### 009 — Segmentation is grounded, soft, and silent
**Date:** 2026-08-29 · **Status:** accepted

Replaces an earlier age-based sketch (`solo_young`, `old_person`) with `party_type`,
`trip_purpose` and `occasion`, all derived from party composition and *explicitly stated*
signals only.

*Why:* inferred age cannot be grounded and fails badly when wrong.

*Constraints:* a ranking bias and add-on filter only — never a hard filter, and never
stated to the guest. "Since you're a family..." is the failure mode. The couples-versus-
friends points-of-interest extension is described in the engineering note, not built.

---

### 010 — Conversation state is durable and event-sourced
**Date:** 2026-08-29 · **Status:** accepted

Append-only event log per conversation; state at turn *n* is a fold over events up to *n*.
Guest messages and system events are the same kind of input.

*Why:* gives UI time travel almost free, makes evals replayable, and is the precondition
for Decision 011 — free to adopt now, expensive to retrofit.

---

### 011 — Owner escalation: architecture now, feature later
**Date:** 2026-08-29 · **Status:** accepted (feature deferred to Phase 7)

Asynchronous human-in-the-loop escalation to the property owner was considered and
postponed. The groundwork is being built (Decision 010, plus a `resolution_path` field on
surfaced unknowns); the feature is not.

*Findings kept for later:* escalation can never block, since owner replies take minutes to
hours; it feels natural on WhatsApp and worse on a web widget, which argues for the
`ChannelAdapter` boundary; there are two distinct kinds, knowledge gaps and authority gaps,
and the second protects revenue; the valuable part is the write-back loop that caches the
owner's answer into the property record with `source: owner_verified`, making each unknown
a one-time cost. Failure modes to handle if built: no reply (TTL plus fallback), duplicate
escalations (dedup on `property_id + question_key`), escalation spam (rate limit), guest
books elsewhere first, reply after the conversation closes.

*Why deferred:* not in the rubric. Phase 1–5 quality beats a sixth feature. If it is not
built, it goes in the engineering note under "what I'd build next".

### 012 — Stack: FastAPI + Pydantic v2 backend, Vite + React + TS + Tailwind frontend
**Date:** 2026-08-29 · **Status:** accepted (revisit)

*Why:* Pydantic v2 gives the LLM's JSON output schema for free from the same models that
type the domain — one definition, not two. Vite is lighter than Next.js given FastAPI is
already the backend; Next would add a server with nothing to do.
